# v0.4B2 — Sales Fulfillment / Dispatch

Delivered:
- persistent fulfillment document and immutable pick lines;
- exact active-reservation pick confirmation;
- one-location fulfillment boundary;
- picked-reservation release lock;
- `sale_issue` Inventory movement type;
- dispatch through `InventoryPoster`;
- weighted-average outbound valuation through existing Inventory valuation;
- atomic reservation consumption before ledger posting;
- fulfillment document is the physical completion state;
- Sales order remains `approved` so current credit exposure is preserved;
- dispatch idempotency;
- generic reversal ownership protection;
- privileged Sales fulfillment reversal;
- inventory-ledger reversal plus replacement active reservations;
- fulfillment and reservation lifecycle audit events;
- MySQL anti-tamper triggers for fulfillment evidence.

API:
- `POST /api/v1/sales/orders/{order}/fulfillments/pick`
- `GET /api/v1/sales/fulfillments/{fulfillment}`
- `POST /api/v1/sales/fulfillments/{fulfillment}/dispatch`
- `POST /api/v1/sales/fulfillments/{fulfillment}/reverse`

This slice deliberately does not implement partial/split fulfillment or delivery
proof. It establishes the invariant that goods leave stock only through the
Inventory ledger and that correction is reversal-based rather than historical
editing.
