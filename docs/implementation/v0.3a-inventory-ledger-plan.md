# v0.3A Implementation Plan — Inventory Ledger Foundation

## Goal

Deliver the smallest production-shaped inventory core that can safely support future procurement and sales posting.

## Increment scope

### Database
- inventory locations;
- inventory movements;
- inventory movement lines;
- inventory balances;
- inventory reservations;
- optional inventory lots;
- required unique indexes and foreign keys.

### Enums
- location type/status;
- movement type;
- reservation status;
- lot status where required.

### Services
- `InventoryPoster`;
- `InventoryBalanceProjector`;
- `StockAvailabilityService`;
- `MovementReversalService`;
- `InventoryTransferService`;
- `InventoryAdjustmentService`;
- `InventoryIdempotencyGuard`.

Keep services narrow. Do not create an inventory God service.

### Security
Add the initial inventory permission set and role assignments.

Use privileged reasons for adjustment/reversal/backdate/negative-stock capabilities.

### Database immutability
Add a privileged SQL hardening script for posted movement tables after the application model is proven.

### API
Implement locations, balance/movement reads, and the first posting commands needed to prove the ledger.

Do not implement the entire procurement UI inside 0.3A.

### Tests
Implement the test cases in the v0.3 testing strategy before adding UI.

## Suggested migration sequence

1. `create_inventory_locations`
2. `create_inventory_ledger_tables`
3. `create_inventory_projection_tables`
4. `create_inventory_reservation_and_lot_tables`

Exact filenames should use the timestamp at implementation time.

## Transaction boundary

Each posting service should perform:

1. resolve organization;
2. validate permission/policy;
3. claim idempotency key;
4. begin DB transaction;
5. lock affected projection rows;
6. validate availability;
7. insert immutable movement;
8. insert immutable movement lines;
9. update projection;
10. write audit event;
11. commit.

Avoid event dispatch that can publish irreversible external side effects before the database transaction commits.

## Deferred from 0.3A

- purchase-order workflow;
- goods-receipt UI;
- supplier invoice workflow;
- three-way matching;
- sales issue posting;
- accounting journal posting;
- advanced costing reports;
- batch expiry alerts.

## Definition of done

- architecture ADR accepted;
- MySQL migrations pass on dev/test;
- ledger posting and reversal are immutable;
- balance projection rebuild works;
- negative stock is blocked by default;
- idempotency test passes;
- transfer conservation test passes;
- organization-isolation tests pass;
- CI is fully green;
- handover updated.
