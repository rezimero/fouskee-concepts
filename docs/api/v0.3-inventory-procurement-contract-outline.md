# v0.3 API Contract Outline

This is an architecture contract, not yet an implemented route list.

All routes remain under `/api/v1`, `auth:sanctum`, `user.active`, `mfa.enrolled`, named permissions, and organization scoping.

## Common posting controls

Physical-stock posting endpoints should require:

- `Idempotency-Key` request header;
- domain permission;
- server-side validation;
- transactional posting;
- immutable audit event.

Sensitive endpoints additionally require `X-Privileged-Reason`.

## Inventory locations

```text
GET  /api/v1/inventory/locations
POST /api/v1/inventory/locations
```

## Balances and movement history

```text
GET /api/v1/inventory/balances
GET /api/v1/inventory/movements
GET /api/v1/inventory/movements/{movementPublicId}
```

Balance queries may filter by location, product, lot, and availability state.

## Inventory commands

```text
POST /api/v1/inventory/receipts
POST /api/v1/inventory/transfers
POST /api/v1/inventory/adjustments
POST /api/v1/inventory/movements/{movementPublicId}/reversals

POST /api/v1/inventory/reservations
POST /api/v1/inventory/reservations/{reservationPublicId}/release
```

No DELETE endpoint removes posted movements.

## Purchase orders

```text
GET  /api/v1/procurement/purchase-orders
POST /api/v1/procurement/purchase-orders
GET  /api/v1/procurement/purchase-orders/{publicId}
PUT  /api/v1/procurement/purchase-orders/{publicId}
POST /api/v1/procurement/purchase-orders/{publicId}/submit
POST /api/v1/procurement/purchase-orders/{publicId}/approve
POST /api/v1/procurement/purchase-orders/{publicId}/cancel
```

PUT is only valid in mutable workflow states such as draft. Approved orders are not silently edited.

## Goods receipts

```text
GET  /api/v1/procurement/goods-receipts
POST /api/v1/procurement/goods-receipts
GET  /api/v1/procurement/goods-receipts/{publicId}
POST /api/v1/procurement/goods-receipts/{publicId}/post
POST /api/v1/procurement/goods-receipts/{publicId}/reverse
```

Posting a receipt creates the inventory ledger receipt atomically.

## Supplier invoices

```text
GET  /api/v1/procurement/supplier-invoices
POST /api/v1/procurement/supplier-invoices
GET  /api/v1/procurement/supplier-invoices/{publicId}
POST /api/v1/procurement/supplier-invoices/{publicId}/submit
```

## Three-way matching

```text
POST /api/v1/procurement/supplier-invoices/{publicId}/match
POST /api/v1/procurement/match-exceptions/{publicId}/approve
```

## Error semantics

Prefer stable domain codes, for example:

- `inventory_insufficient_stock`
- `inventory_idempotency_conflict`
- `inventory_movement_already_reversed`
- `inventory_backdate_not_permitted`
- `procurement_receipt_exceeds_tolerance`
- `procurement_self_approval_not_permitted`
- `procurement_match_exception`
- `procurement_duplicate_supplier_invoice`

React should render these cleanly, but backend policy remains authoritative.
