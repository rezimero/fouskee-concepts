# Handover v0.2 draft — Identity core

## Milestone
0.2A: Organization, Identity, RBAC, immutable Audit, and CI quality gate.

## Implemented
- Organization aggregate with Fouskee defaults: NG, NGN, Africa/Lagos.
- User operational status, public ULID, default organization, MFA-required state, and login/security timestamps.
- Permission catalog with domain-coded permission names.
- Global and organization-scoped system roles.
- Deterministic user-role assignment scope.
- Permission evaluation service.
- Interactive Superadmin bootstrap command.
- Append-only audit-event model.
- Source-controlled MySQL UPDATE/DELETE prevention triggers.
- MySQL-backed authorization and audit immutability tests.
- GitHub Actions quality gate for backend, frontend, dependency audits, and source-file limits.

## Security invariants
- Suspended or disabled users receive no permissions.
- `superadmin` is valid only as a global role.
- Organization roles require an organization scope.
- Audit events are insert-only through the application model.
- Database UPDATE/DELETE against `audit_events` is rejected after privileged hardening.
- Superadmin is marked `mfa_required=true`; MFA enrollment/enforcement is the next identity increment.
- No bootstrap password is stored in source control or seed files.
- CI receives no production, staging, or developer database credentials.

## Database privilege boundary
The runtime Laravel account does not need server-administration privileges.
Trigger installation is separate from ordinary migrations.

Local Windows hardening:

`.\scripts\database\harden-audit-ledger.ps1`

Production must execute the hardening SQL with a controlled deployment
credential, never the runtime Laravel database account.

## Quality gates
Local and CI gates cover:

- Laravel tests against MySQL
- Laravel Pint
- frontend ESLint
- TypeScript/Vite production build
- Composer and npm dependency advisory checks in CI
- 200-line source-file limit

See `docs/operations/ci-quality-gate.md`.

## Next increment
Milestone 0.2B will add first-party SPA authentication, mandatory Superadmin
MFA enrollment, login throttling, authenticated `/api/v1/me`, permission
middleware, session/device controls, and privileged-action reason capture.

## Known limitations
- Off-site/WORM audit replication and cryptographic signing are not implemented yet.
- Role permission caching is deferred until Redis is introduced.
- A dedicated migration/runtime database-account split remains an infrastructure-hardening task before production.
