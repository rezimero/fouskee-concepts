# Handover — v0.3D Inventory / Procurement Workspace

## Baseline

v0.3D extends:

`develop @ 90e26ae`

No new database schema is introduced.

The inventory and procurement hardening triggers installed during v0.3B and
v0.3C remain authoritative and are not reinstalled by this milestone.

## Frontend architecture

Operational code lives under:

`frontend/src/features/operations`

The feature is divided into:

- API adapters;
- inventory/procurement TypeScript contracts;
- formatting/idempotency helpers;
- permission hooks;
- reusable evidence/control components;
- workflow-specific forms;
- workflow pages.

Business decisions remain on Laravel.

## Routing

New protected routes:

- `/inventory`
- `/inventory/counts`
- `/inventory/transfers`
- `/procurement/purchase-orders`
- `/procurement/receiving`
- `/procurement/invoices`

Each route uses the existing `PermissionRoute` and MFA-protected `AppShell`.

## Permission presentation

Mutation buttons use the authenticated permission context:

- `inventory.count`;
- `inventory.adjust.approve`;
- `inventory.transfer`;
- `procurement.manage`;
- `procurement.submit`;
- `procurement.approve`;
- `procurement.receive`;
- `procurement.invoice`;
- `procurement.match`;
- `procurement.exception.approve`;
- `inventory.reverse`.

This is presentation only. Laravel remains the security boundary.

## Privileged reasons

Sensitive decisions use the established `X-Privileged-Reason` header.

The shared privileged-action sheet requires a meaningful reason before it sends
the command.

## Idempotency

Idempotent frontend commands use fresh browser-generated UUID keys.

Retry conflict semantics remain server-controlled.

## Receiving boundary

The workspace deliberately promotes procurement goods receipt, not the direct
inventory receipt API, as the normal operational path.

This preserves:

`PO -> approval -> physical receipt -> supplier invoice -> three-way match`

## Known limitations

### Reference-list scale

Existing master-data helpers request at most 100 suppliers/products. Operational
forms reuse those helpers in v0.3D.

Before catalogs exceed that practical threshold, replace list selectors with a
server-side search/autocomplete contract.

### UI automated testing

The repository does not yet carry a React component/e2e testing framework.
v0.3D therefore uses lint/build plus an explicit browser validation gate.

### Policies

Inventory and procurement policy APIs exist, but dedicated policy editors are
not exposed in v0.3D.

### Direct adjustments and reservations

Backend capabilities remain available but dedicated workspaces are deferred
until their staff personas and fraud controls are designed.

## Verification

Local installer gates:

- Laravel regression;
- Composer validation;
- frontend ESLint;
- production build;
- npm audit;
- source-line limit;
- whitespace check.

GitHub CI must be green before browser validation.
